# MeetPoint 사용자 흐름

## 문서 상태와 기본 전제

- **확정**: 호스트 포함 3~6명의 활성 참가자와 2~5개의 활성 후보를 정상 범위로 사용한다.
- **확정**: 후보는 `후보 시간 + 후보 장소`의 한 쌍이다. 시간과 장소는 입력·검증·설명에서 별도 필드로 유지한다.
- **확정**: 로그인 없이 방 코드와 방 범위 접근 토큰을 사용한다. 토큰은 계정이 아니라 해당 방에서의 작업 권한을 식별하는 임시 자격 증명이다.
- **확정**: 호스트·참여자 토큰은 발급 후 24시간 유효하고 Client의 방별 `sessionStorage`에만 보관한다. 만료·위조 토큰은 `401 TOKEN_EXPIRED` 또는 `401 INVALID_TOKEN`으로 처리한다. 개인 복구 정보는 30일 HttpOnly 쿠키로 보관하고 별도 개인 복구 파일을 다운로드할 수 있다. 접근 토큰과 복구 정보의 수명은 방 데이터 보존 기간과 별개다.
- **미결정**: 방 만료 시간과 만료 후 데이터 삭제 시점은 구현 전에 정한다.

## 전체 흐름

```text
방 생성
  → 후보 시간·장소 등록
  → 링크/코드 공유 및 참여자 입장
  → 후보별 응답 제출·수정
  → (선택) 개인 조건 제출·수정
  → 호스트가 계산 요청
  → 결과와 근거 확인
  → 호스트가 후보 확정
  → 모든 참가자가 확정 결과 재확인
```

## 1. 방 생성

### 주 사용자

호스트

### 정상 흐름

1. 호스트가 모임 제목, 기본 시간대, 자신의 표시 이름을 입력한다.
2. 서버가 `DRAFT` 상태의 `Room`을 만들고 호스트를 첫 번째 `Participant`로 등록한다.
3. 서버가 충돌 가능성이 낮은 6자리 대문자·숫자 방 코드와 호스트 전용 접근 토큰을 발급한다.
4. 클라이언트는 방 코드와 초대 링크를 표시한다. 접근 토큰은 sessionStorage에 보관하고 화면·URL·공유 문자열에 표시하지 않는다. 서버는 개인 복구 쿠키를 설정하고 Client는 안전하게 보관할 개인 복구 파일 다운로드를 제공한다. 개인 복구 파일은 초대용이 아니며 공유하지 않는다.
5. 방에는 아직 후보나 다른 참가자가 없어도 된다. 이 상태에서는 후보 등록과 링크 공유만 할 수 있다.

### 검증

- 제목은 1~80자, 표시 이름은 1~30자다.
- 시간대는 IANA 시간대 문자열을 사용한다. 예: `Asia/Seoul`.
- 방 코드는 대소문자를 구분하지 않고 서버에서 대문자로 정규화한다.
- 이미 확정되었거나 닫힌 방 코드로 새 방을 만들 수 없다.

## 1-1. 기존 참여자의 접근 복구

1. 탭을 다시 열면 보관한 방 주소나 같은 브라우저의 초대 화면에서
   “기존 참여자로 복구하기”를 선택한다. 일반 이름 입력 입장은 새 MEMBER 생성이다.
2. 접근 토큰이 없거나 만료되면 개인 HttpOnly 쿠키로 자동 복구를 한 번 시도한다.
   성공하면 기존 Participant ID·역할·조건·응답·방 상태·계산 결과·Decision을 유지한다.
3. 쿠키가 없거나 만료·폐기되었으면 방 화면에서 보관한 개인 복구 코드를 입력한다.
   개인 파일은 방 주소와 코드를 포함한다. 일반 초대 링크와 공유하지 않는다.
4. 유효한 접근 토큰이 있는 기존 참가자는 Room 진입 시 복구 수단을 등록한다.
   개인 파일 원문을 잃었으면 화면의 재발급 확인을 거쳐 이전 복구 수단을 폐기한다.
5. 모든 자격 증명을 잃으면 기존 권한은 복구 불가다. HOST는 새 방을 만들고,
   MEMBER는 입장이 열린 방에 정원이 있을 때만 새 참가자로 입장할 수 있다.
   재입장은 이전 조건·응답을 승계하지 않으며 복구 실패로 기존 데이터를 삭제하지 않는다.

의견·조건·후보·계산·확정·leave/kick 요청의 인증 오류는 토큰 만료와 무효/누락을
구분해 안내한다. 사용 중인 방 상단의 **다시 불러오기**로 기존 접근 복구를
명시적으로 재시도하고, 실패하면 **기존 참여자 복구**에서 보관한 개인 복구
코드를 입력한다. 현재 방 화면과 작성 중인 초안은 복구 중에도 유지한다.
성공 후에는 원래 작업의 저장/실행 버튼을 사용자가 다시 누른다. 실패한 변경
요청을 성공으로 표시하거나 자동으로 재전송하지 않는다. 새로고침은 저장하지
않은 초안을 잃을 수 있으므로 화면 안의 재시도를 먼저 사용한다. 자동 복구는
방 화면 세션당 한 번이며 만료 사건별 자동 시도로 정책을 바꾸지 않는다.

복구 코드는 발급 후 30일 고정 만료하고 접근 토큰은 24시간이다. LEFT/REMOVED는
복구할 수 없다. CALCULATED/CONFIRMED/CLOSED의 활성 참가자는 복구·조회할 수 있으며
기존 변경 권한 제한은 유지된다. 상세 정책은 `docs/decisions/room-access-recovery.md`를 따른다.

## 2. 후보 시간과 장소 등록

### 정상 흐름

1. 호스트가 후보 추가 화면에서 시작 시각, 종료 시각, 장소명, 주소, 1인 예상 비용, 장소 태그를 입력한다.
2. 서버가 하나의 `Candidate`로 저장한다. `time`과 `place`는 서로 다른 객체로 보존한다.
3. 호스트가 같은 방식으로 후보를 추가하여 2~5개를 만든다.
4. 후보 순서는 호스트가 정한 표시 순서로 저장하며, 점수가 같을 때 마지막 결정적 tie-breaker로 사용할 수 있다.
5. 후보가 수정·보관되면 기존 계산 결과는 `STALE`이 된다. 보관된 후보는 새로운 계산의 대상에서 제외되지만 과거 결과 스냅샷에서는 사라지지 않는다.

### 검증

- 저장 가능한 활성 후보는 최대 5개다.
- 계산·확정 시점에는 활성 후보가 2개 이상이어야 한다.
- 종료 시각은 시작 시각보다 늦어야 하고, 한 후보의 시간대가 방의 기본 시간대와 다르면 명시적으로 저장한다.
- 장소명, 주소는 필수다. 실제 지도 검증은 하지 않는다.
- 1인 예상 비용은 0 이상인 KRW 정수다.
- 동일한 시간 구간·장소 조합은 중복 등록할 수 없다.

## 3. 참여자 입장

### 정상 흐름

1. 호스트가 초대 링크를 보내거나 6자리 방 코드를 공유한다.
2. 참여자가 링크를 열거나 방 코드 입력 화면에서 코드를 제출한다.
3. 서버가 방이 `DRAFT` 또는 `OPEN`이고 정원 6명 미만인지 확인한다.
4. 참여자가 표시 이름을 입력하면 서버가 `JOINED` 상태의 `Participant`와 참여자 토큰을 만든다.
5. 클라이언트는 방의 현재 후보 목록과 본인의 선택 기준 입력 상태를 보여준다. 선택 기준은 입력하지 않아도 후보 응답과 계산을 진행할 수 있다.

Room 화면은 진입 후 기존 REST 조회 API를 짧은 주기로 재호출하고, 브라우저 탭이 다시 활성화되거나 입력 저장이 끝나면 즉시 재조회한다. 이를 통해 참가자 목록, Room 상태, 계산 결과와 Decision 변경을 새로고침 없이 반영한다. 이 방식은 온라인 상태를 판정하거나 다른 참가자의 상세 응답을 공개하는 기능이 아니며, WebSocket·SSE 기반 실시간 동기화도 사용하지 않는다.

### 검증과 제한

- 같은 표시 이름은 허용하지만 참여자 ID는 매번 다르다. 이름은 인증 수단이 아니다.
- Participant lifecycle 결정에 따라 `LEFT`·`REMOVED`는 활성 참가자 집합에서 제외되는 보존 상태다. MEMBER는 `POST /rooms/{roomId}/leave`로 자기 자신만 나갈 수 있고, HOST는 `POST /rooms/{roomId}/participants/{participantId}/kick`으로 같은 방의 활성 MEMBER만 강퇴할 수 있다. 상태 변경 시 해당 token을 즉시 폐기한다.
- `CALCULATING`, `CONFIRMED`, `CLOSED` Room에서는 leave/kick을 차단한다. `CALCULATED` Room에서 변경되면 최신 완료 ScoreResult를 `STALE`로 만들고 Room을 `OPEN`으로 돌린다.
- 나간·강퇴된 Participant와 연결된 Response, 과거 ScoreResult·Decision은 삭제하지 않는다. 방 코드 재입장은 기존 Participant를 복구하지 않고 새 Participant ID와 token을 만든다.
- 만료된 토큰은 `401 TOKEN_EXPIRED`, 위조 토큰은 `401 INVALID_TOKEN`으로 거부한다. 다른 방의 유효한 토큰은 실제 인증 구현과 같이 `404 RESOURCE_NOT_FOUND`로 거부한다.
- 6명이 이미 활성 상태면 입장을 거부한다.
- `CONFIRMED` 상태의 방은 기본적으로 새 참여자를 받지 않는다. 호스트가 재검토 흐름을 연 경우에만 정책에 따라 허용한다.

## 4. 참여자 조건 입력

### 입력 내용

참여자는 필요할 때 자신의 `ParticipantCondition`을 제출·수정한다. 입력하지 않아도 후보별 응답과 계산을 진행할 수 있으며, 입력한 값은 후보 비교를 위한 보조 기준으로 사용한다.

- 가능한 시간대: 예를 들어 `18:00~22:00`, 또는 후보 날짜의 허용 구간
- 1인 최대 예산(KRW): 없으면 제한 없음
- 필수 태그: 반드시 만족해야 하는 조건
- 선호 태그: 만족하면 추가 점수를 받는 조건
- 회피 태그: 후보에 포함되면 충돌로 보는 조건

이동 부담은 일반 조건에 숫자 상한으로 저장하지 않는다. 참여자가 각 후보 응답에서 자신의 체감 부담을 직접 선택한다.

### 정상 흐름

1. 클라이언트가 원하는 경우 가능한 시간대, 예산, 필수·선호·회피 태그를 입력받는다.
2. 서버가 범위와 형식을 검증하고 참여자에게 조건을 저장한다.
3. 조건 제출만으로 후보에 대한 찬성 표가 생성되지는 않는다.
4. 조건이 변경되면 기존 후보별 응답은 유지하고 계산 결과만 `STALE`로 만든다. 참여자는 응답을 다시 제출하지 않고도 새 조건으로 다시 계산할 수 있다.

## 5. 후보별 응답 제출과 수정

### 응답 내용

각 활성 후보마다 다음을 제출한다.

```json
{
  "availabilityStatus": "AVAILABLE",
  "travelBurden": "EASY",
  "note": "회사에서 바로 이동할 수 있어요."
}
```

`availabilityStatus`는 `AVAILABLE`, `MAYBE`, `UNAVAILABLE` 중 하나다. `travelBurden`은 `EASY`, `NORMAL`, `HARD` 중 하나이며 지도 API의 이동시간이나 거리값이 아니다. 예산과 태그 적합성은 후보의 비용·태그와 개인 조건을 비교해 Solver가 계산하므로 응답에서 별도의 찬반 표로 중복 저장하지 않는다.

### 정상 흐름

1. 미응답 후보는 가능 여부를 기본 `MAYBE`(보류)로 표시하지만 미제출 상태다. 이동 부담은 기본 선택하지 않는다. 참여자가 후보별로 가능한 정도와 자기 기입 이동 부담을 입력하고 **의견 저장**을 눌러 제출한다. 선택만으로 저장하지 않는다.
2. Client는 저장된 내 기준과 후보의 시간·예산·필수/회피 특징을 비교해 안내한다. 불가 선택에서도 안내를 볼 수 있고, 충돌이 있어도 직접 선택한 의견을 저장할 수 있다. 서버는 해당 후보가 활성 상태인지 검사한다.
3. 서버가 `ParticipantResponse`를 `SUBMITTED` 상태로 저장한다.
4. 모든 후보에 응답하면 참여자 상태를 `RESPONDED`로 표시한다.
5. 참여자는 계산 전까지 자신의 응답을 수정할 수 있다.
6. 수정이 저장되면 최신 계산 결과는 `STALE`이 되고, 호스트는 다시 계산해야 한다.
7. 참여자가 방을 새로고침하거나 같은 방에 다시 입장하면 Room 조회 응답의 `myResponses`로 자신의 활성 후보 응답을 복원한다. 미응답 후보의 기본 보류는 저장된 응답으로 추정하지 않는다. 저장하지 않은 초안은 새로고침 이후 보존하지 않는다.

### 내 기준으로 의견 채우기

- 내 기준을 먼저 서버에 저장한 뒤 **내 기준으로 의견 채우기**를 누른다. Room에서 불러온 최신 저장 기준을 사용하며 조건 폼의 저장하지 않은 입력은 사용하지 않는다. 저장된 기준이 없으면 버튼을 사용할 수 없는 이유를 안내한다.
- 저장된 의견이 없고 직접 편집하지 않은 활성 후보의 가능 여부만 초안으로 채운다. 이동 부담·메모를 유지하고, 저장된 의견·직접 편집한 초안·저장 중인 후보는 제외한다. 읽기 전용 또는 저장 중에는 적용할 수 없다. 적용/제외 개수를 표시한다.
- 후보 시작·종료가 하나의 가능 시간 구간 안이면 `AVAILABLE`, 부분 겹침·시간 밖·정보 부족/오류이면 `MAYBE`다. 양 끝 경계는 포함하고 여러 구간을 합치지 않는다. 명시적 시간대 offset을 UTC 순간으로 비교한다. 예산·특징 충돌과 선호 특징은 가능 여부를 바꾸지 않는다.
- 자동 입력 이유를 확인하고 필요하면 수정한 뒤 이동 부담을 선택해 **의견 저장**을 누른다. 이동 부담이 없으면 저장을 막고 안내한다. 자동 입력·기본값·조회만으로 응답 API를 호출하거나 `RESPONDED`·coverage를 바꾸지 않는다. 기존 **빠른 의견 입력 → 이 선택으로 모두 저장**은 활성 후보 전체에 선택을 저장한다.
- 주기 조회는 수동/자동 초안을 보존한다. 기준 변경은 현재 조건 안내만 갱신하며 이전 초안을 자동으로 덮어쓰지 않는다. 후보 시간이 바뀌면 이전 자동 이유를 현재 판단처럼 표시하지 않고 “이전 초안 유지, 재확인 필요”를 안내한다. 필요하면 **내 기준으로 다시 채우기**를 누르며, 직접 편집한 후보는 재적용에서도 유지한다.
- 새 활성 후보는 기본 보류이며 다음 적용 대상이다. 보관된 후보는 입력에서 제외한다. 저장 성공 후에만 저장됨으로 표시하고, 실패하면 초안을 유지해 다시 저장할 수 있다. 조건 안내는 시간·예산·특징 비교일 뿐 전체 후보의 완전 일치를 의미하지 않는다.

### 수정 제한

- 본인 응답만 수정할 수 있다. 호스트가 다른 사람의 응답을 대신 수정하지 않는다.
- `travelBurden`은 모든 활성 후보에 필수이며 `EASY`, `NORMAL`, `HARD` 중 하나다.
- 확정된 방에서 응답을 바꾸려면 호스트가 먼저 결과 재검토를 열어야 한다.

## 6. 후보 계산 요청

### 주 사용자

호스트

### 정상 흐름

1. 호스트가 결과 화면에서 계산 요청을 누른다.
2. 서버가 최신 활성 후보, 활성 참가자, 선택 기준(없으면 `null`), 응답을 하나의 입력 스냅샷으로 고정한다.
3. 서버가 해당 스냅샷을 Rust Solver에 전달하고 `ScoreResult`를 `REQUESTED` 또는 `RUNNING`으로 기록한다.
4. Solver가 후보별 점수·순위·근거를 반환한다.
5. 서버가 원본 요청과 결과를 저장하고 방을 `CALCULATED` 상태로 바꾼다.
6. Solver 오류 또는 타임아웃이면 서버가 `ScoreResult=FAILED`를 저장하고 방을 `OPEN`으로 되돌린다.
7. 클라이언트가 결과를 조회하여 후보별 비교 화면을 표시한다.

### 계산 가능 조건

- 활성 참가자 3~6명
- 활성 후보 2~5개
- 개인 조건은 선택 사항이다. 미입력 참여자는 조건 없이 응답을 계산하며 결과에 `CONDITION_NOT_PROVIDED`를 표시한다.
- 계산 중인 요청이 없음

후보별 응답이 일부 빠져 있어도 계산 자체는 가능하다. 이 경우 누락 참가자의 점수 기여를 0으로 두고 `coverage`와 `MISSING_RESPONSE`를 결과에 표시한다. 단, 응답이 완전하지 않으면 최종 확정은 허용하지 않는다.

## 7. 결과 확인

결과 화면은 다음을 한 번에 보여준다.

- 후보 순위와 0~100 총점
- 후보가 모든 조건을 만족하는지 여부
- 응답 커버리지: 예를 들어 `5 / 6`
- 시간·이동·예산·선호별 점수
- 참가자별 점수와 근거
- 필수 조건 충돌, `MAYBE`, 미응답, 자기 기입 이동 부담 표시
- 입력한 개인 기준과 후보가 다르면 응답은 유지하되 `TIME_CONDITION_CONFLICT`, `BUDGET_LIMIT_EXCEEDED` 같은 충돌 근거를 표시
- 개인 기준을 입력하지 않은 참여자는 `CONDITION_NOT_PROVIDED`로 표시
- 완전 일치 후보가 없을 때 `NO_FULL_MATCH` 안내
- 미응답이 없는 계산에서 최고 후보의 점수가 `60.0` 미만이면 `LOW_SCORE` 경고를 표시

결과는 자동 확정되지 않는다. 1위는 추천 순서일 뿐이며, 호스트가 충돌 내용을 확인한 후 최종 후보를 선택한다.

## 8. 최종 후보 확정

### 정상 흐름

1. 호스트가 후보 하나를 선택한다.
2. 서버가 선택한 후보가 최신 `COMPLETED` 계산 결과에 포함되는지 확인한다.
3. 모든 활성 참가자의 모든 활성 후보 응답이 존재하는지 확인한다.
4. 선택 후보가 완전 일치가 아니거나 `LOW_SCORE` 경고가 있으면 호스트에게 불확실성·충돌 목록을 보여주고 `acknowledgeIssues: true` 확인을 받는다.
5. 서버가 `Decision`을 만들고 방을 `CONFIRMED`로 전환한다.
6. 확정된 후보와 계산 스냅샷의 점수·근거를 변경 불가능한 결과로 보존한다.

확정 성공 후 Client는 전용 Decision 조회 결과로 화면을 갱신한다. 호스트는 후보 등록과 응답 입력을 사용할 수 없고, 참여자는 확정 후보·점수·결정 메모리를 읽기 전용으로 확인한다.

### 확정이 거부되는 경우

- 최신 계산 결과가 없거나 후보/응답 변경으로 `STALE`인 경우
- 응답 커버리지가 100%가 아닌 경우
- 계산 결과에 없는 후보를 선택한 경우
- 완전 일치 후보가 아닌데 `acknowledgeIssues`를 보내지 않은 경우
- 호스트 토큰이 아닌 접근 토큰으로 요청한 경우

## 9. 확정 결과 재확인

확정 후 호스트와 참여자는 방 화면을 다시 열어 현재 `Decision`을 조회한다. 결과에는 다음이 포함된다.

- 확정 후보의 시간과 장소
- 확정 시각, 확정한 호스트 참여자 ID
- 확정 당시 계산 ID와 정책 버전
- 후보 총점과 참가자별 근거
- 호스트가 이슈를 인지했다면 그 사유

참여자는 이 화면을 읽기 전용으로 확인한다. 확정 결과는 새로운 알림이나 예약을 자동으로 만들지 않는다.

호스트가 변경을 선택하면 `POST /decision/reopen`에 1~300자의 사유를 보내 명시적으로 재검토를 시작한다. 방은 `OPEN`으로 돌아가고 기존 Decision은 `REOPENED` 상태로 남는다. 후보 또는 응답을 변경하면 기존 계산은 `STALE`이 되고, 새 계산 후 호스트가 다시 후보를 선택해 확정한다. 새 Decision이 저장될 때만 이전 Decision은 `SUPERSEDED`가 된다.

## 예외 상황

| 상황 | 서버 처리 | 화면 안내 및 다음 행동 |
| --- | --- | --- |
| 참여자가 없는 경우(호스트만 있거나 활성 참가자가 3명 미만) | 방 생성과 후보 등록은 허용하지만 계산 요청은 `PARTICIPANT_COUNT_OUT_OF_RANGE`로 거부 | “현재 1/3명 참여”와 초대 링크를 표시하고 참여자를 기다린다 |
| MEMBER가 방을 나가거나 HOST가 MEMBER를 강퇴한 경우 | Participant를 `LEFT`·`REMOVED`로 보존하고 token을 폐기한다. 활성 목록과 다음 계산에서 제외하며 최신 완료 결과는 `STALE`로 만든다 | 나간 사용자는 방 코드로 새 Participant로 다시 입장할 수 있고, 방에는 변경 후 인원과 재계산 필요 상태를 표시한다 |
| 후보가 하나도 없는 경우 | 계산 요청은 `NO_ACTIVE_CANDIDATES`로 거부 | 후보 등록 화면으로 이동시킨다 |
| 후보가 1개뿐인 경우 | 저장은 허용할 수 있으나 계산·확정은 활성 후보 2개 미만으로 거부 | 후보를 하나 더 등록하도록 안내한다 |
| 참여자가 조건을 제출하지 않은 경우 | 계산은 허용하고 해당 참여자의 조건을 `null`로 스냅샷에 포함한다. 결과에 `CONDITION_NOT_PROVIDED`를 표시한다 | 조건 없이도 결과를 확인할 수 있으며, 더 정확한 비교가 필요할 때만 개인 기준을 추가한다 |
| 참여자가 후보에 응답하지 않은 경우 | Solver는 부분 결과를 만들고 후보별 기여를 0으로 처리하며 `MISSING_RESPONSE`를 표시 | 호스트는 결과를 볼 수 있지만 응답 100% 전에는 확정할 수 없다 |
| 모든 후보가 조건을 만족하지 못하는 경우 | `NO_FULL_MATCH` 결과를 정상 반환하고 점수·충돌 수·충돌 내용으로 순위를 만든다 | 호스트가 충돌을 확인하고 `acknowledgeIssues: true`로 최종 선택한다 |
| 미응답이 없는데 최고 후보의 점수가 60.0 미만인 경우 | 계산은 실패시키지 않고 `recommendationWarnings: ["LOW_SCORE"]`를 반환한다 | 호스트가 근거를 확인하고 `acknowledgeIssues: true`로 최종 선택하거나 조건을 수정해 다시 계산한다 |
| 방장이 결과를 다시 계산하는 경우 | 이전 결과는 이력으로 보존하고 새 입력 스냅샷의 계산 ID를 만든다 | 최신 결과와 이전 결과의 기준 시각을 구분해 표시한다 |
| 확정된 결과를 변경하는 경우 | 호스트가 사유와 함께 재검토를 열면 방이 `OPEN`으로 돌아가고 기존 결정은 `REOPENED`가 된다. 새 계산 후 새 결정을 확정한다 | 기존 확정 결과는 이력으로 남고 새 확정 시 `SUPERSEDED`로 표시한다 |
| 잘못된 초대 코드로 접근하는 경우 | `ROOM_NOT_FOUND_OR_INVALID_CODE`를 404로 반환하며 방 존재 여부를 상세히 노출하지 않는다 | 코드 재입력 또는 새 초대 링크 요청을 안내한다 |
| 계산 중 다시 계산을 요청하는 경우 | 중복 요청을 409 `CALCULATION_IN_PROGRESS`로 거부 | 기존 계산 상태를 조회하도록 안내한다 |
| Solver 오류 또는 타임아웃 | `ScoreResult=FAILED`를 저장하고 방을 `OPEN`으로 되돌린다 | 오류 코드와 재시도 가능 여부를 표시하고 호스트가 다시 계산한다 |
| 후보·조건을 계산 후 수정하는 경우 | 최신 결과를 `STALE`로 표시하고 확정 요청을 거부 | 호스트가 다시 계산해야 한다 |

## 확정 사항과 미결정 사항 요약

- **확정**: 계산은 호스트가 명시적으로 요청하고, 확정은 호스트가 별도로 수행한다. 결과는 자동 확정하지 않는다.
- **확정**: 미응답은 찬성으로 간주하지 않으며, 부분 결과 표시와 최종 확정 제한을 모두 적용한다.
- **확정**: `CLOSED`는 방 만료·관리 작업을 위한 예약 상태이며 현재 사용자 흐름과 외부 API에는 방 닫기 기능을 넣지 않는다.
- **미결정**: 방 만료·삭제 정책, 확정 후 새 참여자 허용 여부는 추후 결정한다. HOST 승계와 계정 기반 영구 차단은 별도 정책으로 다룬다.
